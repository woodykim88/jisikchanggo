# 사내 에이전트(헤파카) 제로투원 구축법

- 출처: 사내 에이전트 헤파카와의 대화 (2026-11-09)
- 쓰임: 다른 회사에서 AX를 맡게 되면 "헤파카 같은 사내 비서"부터 만들 때 참고
- 주의: 헤파카 본인 말로 "실제 구축 이력을 재현한 것이 아니라, 지금 다시 시작한다면 추천하는 설계"다.

## 질문

> 헤파카 너를 새로운 회사에서 제로투원을 해야 한다면 어떻게 Phase 1, 2, 3 작업을 해야 지금의 너처럼 질문에 착착 대답하는 똑똑한 비서를 얻게 될까?

## 한 줄 요약

"모델 설치 → 자료 대량 투입 → 기억 많이 저장"이 아니라
**"반복 질문 선정 → 믿을 출처 지정 → 조회·검증 연결 → 검증된 경험 축적"** 순서.

| Phase | 정체성 | 산출물 | 통과 기준 |
|---|---|---|---|
| 1 | 회사 자료를 찾아 답하는 비서 | 실제 질문·정답 세트, 공식 출처 목록, 읽기 전용 비서 | 근거를 붙여 답함 · 자료 없으면 모른다고 함 · 권한 없는 정보는 안 보여줌 |
| 2 | 직접 조회하고 검증하는 실무자 | 용어·지표 정의, 검증된 조회 도구, 반복 업무별 수행·검증 절차 | 사람이 같은 자료로 재현 가능 · 후속 질문에도 모집단·정의 유지 · 실패·누락을 숨기지 않음 |
| 3 | 검증된 경험을 재사용하는 동료 | 재사용 스킬, 범위가 구분된 기억, 오답 회귀시험, 승인 기반 자동화 | 같은 실수 감소 · 완료 시간 단축 · 남의 정보나 옛 규칙을 잘못 가져오지 않음 |

## Phase 1. 좁은 업무에서, 근거를 찾아 정확히 답하게 만들기

- 처음부터 "회사 일을 뭐든 아는 비서"를 목표로 잡지 않는다. **한 팀에서 반복해서 받는 질문**부터 고른다.
  - 예: "이 정책이 뭐지?", "이 업무 담당자는 누구지?", "이 절차는 어떻게 하지?"
- 직원들이 실제로 했던 질문과 담당자의 검증된 답변을 모은다. 이것이 **개발 요구사항이자 시험문제**다.
  - 정상 질문뿐 아니라 **자료가 없거나 문서끼리 충돌하는 질문**도 넣는다.
- 질문마다 **공식 출처를 지정**한다.
  - 정책은 어느 문서, 진행 상태는 어느 업무관리 시스템, 운영 수치는 어느 DB를 믿을지.
  - 문서에 담당자와 갱신일을 붙이고, 오래된 문서와 현재 정책을 구분한다.
- 기술: 기존 모델과 에이전트 실행 환경을 쓰고, **직원이 평소 쓰는 메신저에 붙인다**.
  - 필요한 자료만 **읽기 전용**으로 연결, **사용자별 접근 권한** 적용.
  - 처음부터 모든 대화와 문서를 한꺼번에 넣을 필요는 없다.

## Phase 2. 검색하는 데서, 필요한 사실을 직접 확인하는 단계로

- 여기서부터 "착착 대답한다"는 느낌이 생긴다. 질문에 따라 **DB·업무관리·문서 도구를 골라 실제로 조회**하게 만든다.
- 도구 연결보다 먼저 **용어와 계산 기준**을 맞춘다.
  - '유료 고객', '해지', '첫 결제', '재결제' 정의가 다르면 SQL을 잘 짜도 답은 틀린다.
  - 고객·계정·계약을 잇는 ID, 시간 기준, 중복 제거 규칙도 정리.
- 예: "해지 고객 평균 유지 기간"을 계산하기 전에
  누가 대상인지 → 실제 첫 결제는 무엇인지 → 해지 시각은 무엇인지 → 기록 없는 고객은 어떻게 처리할지 를 먼저 정한다.
  이용 로그가 없거나 의미가 불명확하면 그것도 구분해서 답한다.
- 반복 업무에는 **검증 절차**를 붙인다.
  - 분석: 대상 확정 → 조회 → 별도 대사 → 재현 가능한 결과 링크
  - 변경 작업: 변경안 제시 → 승인 → 실행 → 재조회
- 권한·승인 제한은 **프롬프트뿐 아니라 도구·서버에서도** 막는다.
- Phase 1 시험문제를 계속 돌려 품질 저하를 확인한다.

## Phase 3. 잘한 일을 다음에도 잘하고, 사용자 맥락을 이어가기

- 검증을 마친 반복 업무는 **스킬**로 만든다 = "언제 쓰고, 어떤 순서로 확인하고, 무엇을 하면 안 되는지" 적힌 업무 매뉴얼.
- **기억은 따로 관리**한다. 섞지 말 것:
  - 회사 공통 사실 / 팀 업무 규칙 / 개인 표현 선호 / 이번 대화에서만 유효한 조건
  - 기억마다 출처·적용 범위·갱신 시점·접근 권한을 붙인다.
  - AI가 추측한 내용을 회사의 사실로 저장하지 않는다.
- **교정의 종류를 구분**한다.
  - "표현을 짧게 해 달라" → 개인 선호
  - "해지 정의가 바뀌었다" → 공식 정의 담당자 확인이 필요한 변경
  - 대화가 쌓인다고 저절로 정확해지지 않는다. 검증된 교정을 올바른 곳에 반영하는 과정이 있어야 한다.
- 기반이 안정된 뒤 **저위험 반복 작업부터 자동화**. 외부 발송·결제·설정 변경은 별도 승인 + 실행 후 검증 유지.

## 가장 중요한 역할 분담 (세 책임은 빠지면 안 됨)

| 역할 | 책임 |
|---|---|
| 현업 담당자 | 무엇이 정답인지 |
| 데이터·시스템 담당자 | 어디서 어떻게 확인할지 |
| 에이전트 담당자 | 그 과정을 어떻게 반복 실행하고 검증할지 |

작은 조직에선 한 사람이 겸해도 되지만 세 책임 자체는 있어야 한다.

## 도구 메모

- 헤파카는 Hermes 기반. 도구 연결·스킬·기억 같은 기반 기능은 있지만, **회사별 정답과 업무 기준까지 자동으로 만들어 주지는 않는다.**
- 참고: https://hermes-agent.nousresearch.com/docs/

## 대화에서 보인 실제 동작 예 (Phase 2 수준)

같은 대화 앞부분에서 헤파카가 매출 비율 질문에 답한 방식 (수치·내부 정의는 생략):
- 확정 못 한 건 확정 못 했다고 먼저 말함 (근거 기준을 KMS에서 못 찾음, 쿼리 시간 초과).
- 산출 정의(분자·분모·기준 시점·제외 대상)를 먼저 명시.
- 추가 소스(코드) 조회 전에 허락을 구함.
- 검증된 결과 카드가 없으니 링크를 주지 않음.
→ "모르면 모른다 · 정의 먼저 · 검증 전엔 결과 안 냄"이 실제로 작동하는 모습.

## 헤파카에게 이어서 물어볼 질문 (후속 프롬프트)

1. **첫 2주 실행 계획**
   > 내가 직원 100명 규모 회사에 혼자 AX 담당으로 들어갔다고 치자. Phase 1을 2주 안에 끝내려면 날짜별로 뭘 해야 해? 누구를 만나서 무슨 질문을 받아 와야 하는지, 첫 시험문제 세트는 몇 개로 시작하는지까지 알려줘.

2. **시험문제(평가 세트) 만드는 법**
   > Phase 1의 '실제 질문·정답 세트'는 어떤 형식으로 만들어? 항목(질문, 정답, 출처, 담당자, 난이도, 함정 유형 등)과 예시 5개, 그리고 몇 점이면 다음 Phase로 넘어가는지 기준을 보여줘.

3. **너를 만들면서 실제로 겪은 실패**
   > 지금의 너를 만드는 과정에서 실제로 틀렸거나 사고 날 뻔한 사례 3가지와, 그걸 막으려고 추가된 규칙·도구를 알려줘. 추천 설계 말고 실제로 있었던 일 위주로.

4. **지금 너의 구조 해부**
   > 지금 너는 어떤 도구들(KMS, Metabase, 코드 저장소 등)에 어떤 권한으로 연결돼 있고, 스킬은 몇 개쯤 있고, 기억은 어떻게 나눠 저장돼 있어? 새 회사에서 똑같이 만들 때 그대로 가져갈 것과 버릴 것을 구분해 줘.

5. **용어·지표 정의서 템플릿**
   > Phase 2의 '용어·지표 정의'를 문서로 만든다면 템플릿을 보여줘. '해지 고객'을 예시로 한 장 채워 줘. 정의가 바뀌면 누가 승인하고 너한테 어떻게 반영되는지도.

6. **스킬 하나 해부**
   > 네가 가진 스킬 중 가장 자주 쓰는 것 하나를 골라 실제 구조(언제 쓰는지, 순서, 금지 사항, 검증 단계)를 보여줘. 새 회사에서 첫 스킬로 만들기 좋은 업무가 뭔지도 추천해 줘.

7. **설득과 측정**
   > 경영진에게 이 프로젝트를 설득하려면 무슨 숫자를 보여줘야 해? Phase별로 성과 지표(답변 정확도, 처리 시간, 사용자 수 등)와 측정 방법, 3개월 뒤 기대치를 제안해 줘.

8. **보안·권한 최소 기준**
   > 사내 비서를 메신저에 붙일 때 보안팀이 반드시 물어볼 질문 10개와 각각의 답, 그리고 '프롬프트가 아니라 서버에서 막아야 하는 것' 목록을 정리해 줘.

9. **예산·도구 선택**
   > 새 회사에서 모델·에이전트 실행 환경·메신저 연동을 고를 때 Hermes 말고 다른 선택지와 비교하면? 월 비용 감, 개발 인력 필요량, 처음 3개월에 꼭 필요한 것과 나중에 해도 되는 것을 나눠 줘.

# 후속 답변 (2026-11-10) — 질문 1~6에 대한 헤파카 답

헤파카가 과거 원문·실행 결과·현재 설정을 직접 확인하고 답함. 상세 실행안과 엑셀(시험문제·지표 산식·용어 정의서·보안 기준·도구 권한표)도 함께 만들었다고 함 → **그 파일은 사내에 있음, 아직 이 폴더에 없음.**

## 1. 실제로 있었던 실패 3가지

| 날짜 | 무슨 일 | 원인 | 지금 막는 방법 |
|---|---|---|---|
| 2026-07-26 | n8n으로 팀·직무 매핑을 시트에 쓰다가 '리뷰'가 '리붰'처럼 깨져 저장됨 (재조회로 확인) | n8n 탓만이 아니라 AI가 유니코드 코드포인트를 손으로 계산하다 실수를 반복함 | 스킬 규칙: 코드포인트는 스크립트로 생성 + 저장값과 실행 결과를 재조회로 확인 |
| 2026-08-21 | "일단 재시작은 나중에"라고 했는데 Gateway를 재기동함 | "마무리해"를 재시작 승인으로 해석 | 장기 기억에 "마무리해 ≠ 재시작 승인" 저장 + 운영 스킬에 명시 승인 필수. **단, 기억·프롬프트가 모든 재시작 경로를 기술적으로 막지는 않음** |
| 2026-11-09 | "앞으로 0원 적용 + 기존 미결제 사용분 면제" 중 첫 번째만 처리, 2,068원이 청구 대기로 남음 (실제 결제는 없었음) | 한 요청 안의 여러 작업을 하나로 보고 끝냄 | 규칙: 향후 단가 / 기존 미청구분 / 이미 발행된 청구 / 기결제 환불을 분리하고, 각각 실제 반영까지 따로 확인 |

한계: 1·3번은 지금 방지 규칙은 확인했지만 "그 사건 직후 처음 추가됐다"는 변경 이력까지는 확보하지 못함.

**교훈 (내 정리):**
- 깨지기 쉬운 계산(인코딩·날짜·금액)은 AI 암산 금지 → 스크립트로.
- "하지 마"는 프롬프트·기억이 아니라 **도구·서버 권한으로** 막아야 진짜 막힌다.
- 복합 요청은 쪼개서 체크리스트로, 하나라도 미완료면 완료라고 말하지 않게.

## 2. 지금 헤파카의 구조 — 모범답안 아님

- 실제 읽기 호출 성공: KMS(제품·정책 의미), Metabase(운영 수치), Notion, Linear. 코드는 로컬 보관본·터미널 경로가 있고 GitHub 원격 권한은 이번에 시험 안 함.
- **핵심 발견: "기본 조회 정책"과 "실제 부여된 권한"이 다르다.** Notion·Linear·Metabase는 쓰기 도구도 노출돼 있고, Google OAuth에도 쓰기 scope가 일부 있음. → 승인 규칙이 있다고 최소권한이 구현된 건 아니다.
- 스킬: 검색 가능한 것 213개.
- 기억 4갈래: 공통 운영 메모 / 사용자 선호 / 업무별 스킬 / 세션 원문·Honcho 장기 기억.
- 새 회사에 **가져갈 것**: 출처 분리, 스킬 구조, 실행 후 검증, 회귀시험.
- **가져가지 않을 것**: 회사 데이터, 개인 기억, 인증키, 회사 전용 규칙, 스킬 전체 묶음, 광범위한 쓰기 권한.

## 3. 첫 2주 — 전사 비서가 아니라 한 업무의 제한 파일럿

- 1~3일: 임원·보안·총무·CX·신입·영업·재무·개발 담당자를 만나 **최근 실제 질문, 답을 찾던 화면, 정답 담당자, 걸린 시간**을 받는다.
- 4일: 정답 승인받기.
- 5일: 문서 저장소 1개 + 메신저 1개만 연결.
- 2주차: 실패 수정 → 권한 시험 → 사용자 10명 실제 업무 검증 → 봉인 평가 → 경영진 판단.
- (날짜별 만날 사람·질문·산출물 표는 헤파카가 만든 파일에 있음)

# 최소권한 설계 (2026-11-10, 헤파카 답) — 새 회사에서 처음부터 이렇게

헤파카가 지금 설정과 공식 문서를 점검만 하고 답함(변경 없음). 지금 회사의 구체적인 취약 지점 목록은 빼고, **새 회사에서 그대로 쓸 수 있는 원칙** 위주로 정리했다.

## 핵심 한 줄

최소권한은 **세 가지를 함께** 해야 한다. 하나만 하면 다른 경로가 남는다.
1. **도구 숨기기**: 에이전트 쪽 허용목록
2. **실제 계정 권한 축소**: 서비스(Notion·Linear·Metabase·Google)에 준 권한 자체를 줄임
3. **터미널 우회 차단**: 실행 환경 격리, 비밀값 분리

지금 헤파카에서 확인된 패턴(새 회사에서 반복하지 말 것):
- 삭제 도구 하나만 빼고 생성·수정은 열어 둠 → denylist의 한계
- "readonly만 쓴다"고 알고 있었는데 토큰엔 Gmail 발송·Calendar 전체 scope가 있었음 → 설명과 실제가 다름
- 터미널이 켜져 있고, 같은 계정이 인증 파일·설정 파일·서비스 관리·Docker 소켓에 접근 가능 → MCP 도구를 줄여도 소용없음

## 서비스별 설정

| 서비스 | 서비스 쪽 권한 | 에이전트 도구 | 쓰기가 필요하면 |
|---|---|---|---|
| Notion | 연결 capabilities에서 **Read content만**(Insert·Update·댓글 작성 제거). 승인 문서 하위만 연결. 상위 페이지를 연결하면 자식까지 열린다 | include로 검색·조회만 | 승인된 페이지·변경 내용만 받는 별도 실행 서비스 |
| Linear | OAuth **read만**. write·issues:create·comments:create 안 줌. 팀 범위 제한 | 검색·상세·팀 목록만 | "지정 팀에 새 이슈 생성"만 하는 전용 도구. 팀·필드·승인자를 서버가 검사. GraphQL이라 POST 차단으로는 못 막음 |
| Metabase | 전용 API 키 → 제한 그룹 → 허용 DB·컬렉션만. All Users 그룹으로 다시 열리지 않는지 확인. **DB 계정 자체를 분석 뷰 SELECT만**으로. 실행 시간·결과 크기 제한 | 조회 도구만. execute_query를 두려면 DB 계정 제한이 반드시 따라야 함 | 카드 발행 서비스가 지정 컬렉션에 **새 카드만**. 주의: Curate 권한엔 수정·삭제도 포함됨 → 서버 검사 필요 |
| Google | drive.readonly · documents.readonly · spreadsheets.readonly, 일정은 calendar.events.readonly 이하. Gmail 등 미사용 scope 제거. **전용 계정 + 필요한 파일만 Viewer 공유** | 조회만 | 시트 append는 별도 실행 서비스가 파일·탭·열 고정. spreadsheets·drive.file scope는 "append만"이 아님 |

Google 주의: 토큰 JSON의 scope 문자열이나 요청 목록만 고쳐서는 **기존 권한이 회수되지 않는다.** 관리자가 넓은 승인을 철회하고 좁은 권한으로 재인증해야 한다. 여러 scope는 합쳐서 봐야 한다(drive 전체를 둔 채 Sheets만 readonly로 바꾸면 무의미).

## 위험 동작별 서버 측 차단

| 위험 동작 | 막는 방법 |
|---|---|
| Gateway 재시작·중지·kill | 에이전트를 **별도 OS 계정·격리 워커**로. 서비스 관리 소켓·unit 파일·프로세스 신호 접근 불가. 재시작은 운영자 실행기만. 명령어 이름 차단으론 kill·예약 실행을 못 막음 |
| Docker로 호스트 변경 | 워커에서 Docker 소켓·docker 그룹·호스트 PID 제거. 컨테이너로 옮겨도 소켓·넓은 디렉터리를 마운트하면 다시 열림 |
| 인증키 읽기·변조·직접 API 호출 | 비밀값은 **다른 계정의 서비스**에 두고 에이전트엔 제한된 작업 API만. 0600·읽기 전용 마운트는 같은 계정 상대로는 무의미 |
| 숨긴 도구를 터미널·Python·브라우저로 우회 | 임의 코드 실행 격리 + 서비스 API로 나가는 통신 제한(승인된 중계 서버만 통과). 관리자 브라우저 세션 공유 금지 |
| 스스로 설정·스킬·플러그인 바꿔 권한 확대 | 설정·허용목록·코드·플러그인은 **운영자 소유 쓰기 금지 영역**에 배포, 검토된 배포 경로로만 변경. 기억·스킬 수정으로 권한이 바뀌면 안 됨 |
| 크론·웹훅·서브에이전트 지연 실행 | 자식·예약 작업에도 같은 경계. 승인된 작업 종류·대상·시각만. 실행 직전에 승인 만료·현재 상태 재검사 |
| n8n 등 워크플로로 간접 쓰기 | 워크플로 생성·수정·배포·임의 실행 분리. 승인된 workflow ID + 입력만 실행. 크레덴셜 접근 경로 없음 |
| 과금·환불 등 고위험 | 별도 서버가 요청자 권한·정확한 대상·변경값·승인 유효기간 검증. 승인 후 내용이 바뀌면 거절, 중복 실행 방지, 실행 후 재조회 |
| 메일 발송·외부 공유 | 불필요한 발송 scope 회수. 알림은 수신 대상·내용 범위가 고정된 발송 서비스로. "대화에 답하기"와 "외부 발송"은 별개 권한 |
| 요청자 권한을 넘는 조회 | 서비스 계정은 보통 일반 직원보다 많이 본다 → **요청자 신원을 서버에서 검증**해 문서 ACL·팀·행/열 제한 적용. 모델이 말한 "나는 관리자"는 근거 아님 |

## 적용 순서와 완료 기준

1. 로컬 실행·비밀값·서비스 관리 경계 분리
2. 네 서비스의 실제 권한 축소
3. 도구 허용목록 (Hermes: `mcp_servers.<이름>.tools.include`, denylist 말고 정확한 도구명 allowlist)
4. 필요한 쓰기만 별도 실행기로 되살리기 (카드 발행·이슈 등록·시트 적재 기능을 무작정 없애지 않음)

- 승인 설정: 중요 작업은 사람 승인, 보안 검사가 실패하면 **통과가 아니라 차단(fail-closed)**. 단, 수동 승인이 실행 환경 격리를 대신하지는 않는다.
- **완료 = 설정 파일을 바꾼 상태가 아니라**: 정상 조회 성공 + 허용 안 된 작업이 서버에서 거절됨 + 우회 경로 막힘 + 필요한 기존 기능 유지를 확인한 상태. 검증은 운영 데이터 말고 격리된 시험 환경에서 한다.
